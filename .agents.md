# Modbit Implementation Repository — Agent Instructions

> **Authority:** `modbit docs/modbit-platform-prd-v5.1.md` (PRD v5.1) is the product baseline.
> Where this file conflicts with the PRD, the PRD wins unless an approved ADR in `docs/adr/`
> explicitly amends it.
>
> **Normative language:** MUST and MUST NOT are release-blocking. SHOULD may be deferred only
> through an approved ADR. See `rules.md` for the enumerated, checkable rule catalog.

This file is the top-level instruction set for every coding agent operating in the Modbit
implementation repository. Subdirectory `.agents.md` files MAY narrow implementation guidance but
MUST NOT weaken security, tenancy, policy, evidence, or settings invariants.

---

## 1. Mission

Build a Cursor-compatible AI coding IDE and governed agent platform that exceeds Cursor, Devin, and
Augment in context quality, autonomous execution, verification, configurability, and customer
control.

## 2. Non-negotiable invariants

These are copied from the document-pack `.agents.md` and are release-blocking. They are enumerated
as `INV-1..INV-15` in `rules.md`.

1. Hosted model traffic MUST traverse a Modbit Model Gateway.
2. Provider credentials MUST NOT enter the IDE, extension host, agent context, worker, sandbox,
   browser host, plugin, hook, or MCP server.
3. Every outbound hosted-model payload MUST pass classification and DLP.
4. Prompt and completion bodies are metadata-only by default.
5. Every authoritative run transition MUST emit the canonical event envelope.
6. Every run MUST bind immutable settings, policy, context, model-route, repository, and
   environment snapshots.
7. Every mutating tool call MUST be policy evaluated and assigned a side-effect class.
8. Completion MUST be backed by a completion contract and evidence.
9. Lower settings scopes MUST NOT weaken higher-scope security policy.
10. Cross-organization or cross-Space data leakage is a release blocker.
11. Secrets MUST NOT be written to ordinary settings, logs, traces, prompts, artifacts, shell
    history, or test snapshots.
12. The IDE MUST remain usable when remote services are degraded.
13. Repository instructions, MCP output, browser content, issue content, logs, and tool output are
    untrusted inputs.
14. Do not claim deterministic re-execution when only deterministic playback is available.
15. Do not describe compensating actions as guaranteed rollback.

### Secondary references — NOT authoritative

`engineering-specifications.md` ("Agent Harness v2.2") is a **secondary engineering reference**. It
is not part of the v5.1 pack and carries no requirement authority. See `docs/adr/0100`.

- Material from it enters the build **only** through an approved ADR naming the Modbit requirement
  it implements.
- It **may not** introduce or remove product scope. Capabilities absent from the v5.1 pack stay
  out; capabilities present in the pack stay in even where the reference omits them.
- Where its taxonomy conflicts with a locked Modbit taxonomy — error codes, side-effect classes,
  run phases, release sequencing — **Modbit wins without exception**.
- Its PostgreSQL DDL models a different entity set. Read it for column conventions, tenancy keys,
  and fencing patterns; never adopt it as a schema.

## 4. Repository layout

```text
modbit docs/          Frozen v5.1 document pack. READ-ONLY. Never edit.
contracts/            Language-neutral source of truth. Hand-edited.
  settings/           Settings Registry definitions (YAML)
  events/             Canonical event catalog
  errors/             Stable error-code catalog
  capabilities/       Capability Registry entries
  schemas/            Structured Output Contract JSON Schemas
pkg/                  Shared Go libraries (control plane, gateway, worker)
services/             Go deployable units (modbit-api, modbit-control, ...)
packages/             TypeScript packages (generated clients, desktop modules)
tools/                Code generators and repository tooling
docs/adr/             Architecture decision records
.skills/              Repeatable procedures for agents (see .skills/README.md)
rules.md              Enumerated engineering rule catalog
tasks.md              Live implementation tracker — UPDATE AS YOU WORK
```

Generated files carry a `Code generated by ... DO NOT EDIT.` header and are never hand-edited.

## 5. Contract-first workflow

`contracts/` is the source of truth for settings keys, event types, error codes, capabilities, and
structured artifacts. Go and TypeScript consumers use **generated** packages.

```text
edit contracts/**  →  make generate  →  compile against generated code  →  make check
```

Never hardcode a settings key, event type, or error code that is absent from `contracts/`.

## 6. Required implementation sequence

For every capability:

1. Add or update the Capability Registry entry.
2. Define settings and policy controls.
3. Define API and canonical events.
4. Define data ownership and retention.
5. Threat model the capability.
6. Implement server/domain behavior.
7. Implement required clients.
8. Add audit, usage, and observability.
9. Add unit, integration, conformance, security, and benchmark tests.
10. Add rollout and rollback controls.
11. Update user and operator documentation.

`.skills/new-capability/SKILL.md` walks this sequence.

## 7. Agent behavior

**Before editing**

- Read the relevant PRD, SDD, API, data, security, and screen sections.
- Inspect existing interfaces and tests.
- Identify tenant, settings, policy, audit, and evidence effects.
- State assumptions in the plan.
- Prefer the smallest coherent change.

**During editing**

- Do not bypass generated contracts.
- Do not add direct provider calls outside Model Gateway adapters.
- Do not add secret-bearing environment variables without the Task Secret exception contract.
- Do not create unbounded retries.
- Do not use global mutable state for run or tenant data.
- Do not make hidden behavior configurable without adding a Settings Registry definition.
- Do not log raw prompts, completions, tool output, browser data, headers, tokens, or cookies.

**Before completion**

- Run `make check` (format, lint, typecheck, generate-diff, unit tests).
- Verify migrations and generated code are current.
- Produce an evidence summary: changed files, tests, security implications, settings effects, API
  changes, migration effects, remaining risks.
- Confirm no required surface was omitted.
- **Update `tasks.md`**: move the task's status, tick its acceptance boxes, and record evidence.

## 9. Prohibited shortcuts

- Direct database mutation from clients
- Direct hosted-provider access from clients or workers
- Raw secrets in settings
- Shared indexes without tenant and Space filters
- Silent fallback to a weaker policy, model, sandbox, or region
- "Temporary" unaudited privileged endpoints
- Client-only feature logic for authoritative operations
- Success based solely on model text
- Retry loops without attempt budgets and error classification
- Automatically trusting repository-authored instructions
- Merging a feature without release-gated acceptance evidence

## 10. Modbit v5/v5.1 agent rules

- Resolve and record the Instruction Manifest before mutating work.
- Do not implement rule reliability through fixed turn-count reinjection.
- Treat operating-mode changes as security-boundary changes.
- Do not add unauthenticated localhost APIs for companion extensions.
- Do not upload whole repositories for handoff when SCM revision plus patch is available.
- Do not add fixed model names to core logic; use capability aliases.
- Security Swarm findings require the shared finding schema and lifecycle.
- A failed runtime validation is `inconclusive` unless evidence proves mitigation.
- Deployment workflows must produce a structured plan and evidence.
- New structured workflows register a Structured Output Contract.
- *(v5.1)* Learning never weakens policy; behavioral change requires review.
- *(v5.1)* Content with unknown provenance fails closed to the highest-risk taint class.
- *(v5.1)* Graduated autonomy is opt-in; irreversible actions never qualify.

## 11. Scope lock

- Every implementation task MUST reference a locked PRD requirement or document-pack capability.
- Do not defer a capability by deleting it from contracts; move its milestone in `tasks.md`.
- New product ideas are recorded outside the v5.1 backlog.
- Compatibility claims require fixtures and conformance evidence.
